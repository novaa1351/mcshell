# M9 — Production: from one machine to anyone's

M0–M8 built a shell that works on one laptop, installed from a checkout, by the
person who wrote it. M9 is everything between that and a stranger installing
it from a README. **No new features.** A session that starts adding behaviour
has left M9, the way a polish session that writes install docs had left M8.

Decided 2026-10-14: **an Arch package comes first, and nothing else ships
until it is installable on a machine that is not this one.** The reasoning is
in *Arch first, or everything at once* below.

## The order

Each step depends on the ones above it. The first two are decisions, not code,
and both block the repository going public — which blocks the AUR, because an
AUR package must point at public source.

### 1. Decide the things that cannot be changed later

- **License** — see *Licenses: what each one costs* below. Before the first
  public commit: changing it later needs the consent of everyone who has
  contributed.
- **Name and logo against Mojang's usage guidelines.** Read the current
  guidelines first-hand rather than relying on a summary. The questions:
  whether "MCShell" reads as using the Minecraft brand in a product name, and
  whether a grass-block logo implies affiliation. Add the "Not an official
  Minecraft product. Not approved by or associated with Mojang or Microsoft."
  line to the README and the mod's metadata regardless.
- **What is never shipped.** Already true and worth writing down as a rule:
  no Mojang asset is redistributed. The lock screen, boot screen and toasts
  read the user's *own* client jar at runtime; the mod jar contains only our
  classes and a refmap.

## Footprint

People choosing a desktop ask what it costs at idle, so it is part of shipping.
Measure with `session/probes/footprint.sh` — compare its `own` total, and
compare from a fresh game start at matching uptimes (`--line`, once a minute),
never one snapshot against another. Started 2026-10-14, all measured:

| Change | Result |
|---|---|
| Overlay draws in software (`GSK_RENDERER=cairo`) | 167 → 78MB; no context on the dGPU; less CPU |
| Heap floor 128M, free ratios 10/30, periodic GC 60s | game 1,248 → 1,110MB at 16 min; ~2ms pauses, once a minute |
| `MALLOC_ARENA_MAX=2` in `launch.sh` | game 1,110 → 977MB at 16 min; 16 malloc arenas holding 225MB → 3 holding 63MB; CPU within noise |

Left, in order of value: mipmap levels 4 → 0 (a taste call: it changes how
distant blocks look); nothing else in the shell's own processes is worth the
risk. Ruled out: closing Prism after launch (the unit tracks it), a native
Wayland game to drop Xwayland (a large change to the pointer handshake), and a
lower `-Xmx` (an out-of-memory crash takes the desktop with it). On a typical
machine the browser outweighs the whole shell.

## Licenses: what each one costs

Not legal advice — the practical consequences, so the choice is an informed
one.

**The fact that shapes all of it:** the mod links against Minecraft, which is
proprietary. The GPL's "system library" exception does not cover a game, so a
GPL-licensed *mod* is in a long-standing grey area: the license asks that the
combined work be distributable under the GPL, and Minecraft cannot be. Nobody
is known to have been pursued over it, but it is why the Fabric ecosystem
mostly uses MIT, Apache-2.0, LGPL or MPL — and why the Fabric loader and
Fabric API are Apache-2.0. The daemon and the session scripts do not link
against Minecraft at all; for them the choice is free.

So the realistic options are one license for everything, or **one for the mod
and one for the rest**.

### MIT (or Apache-2.0)

What you lose:

- **Control over forks.** Anyone may take the code, close it, rebrand it and
  sell it, and owes you nothing but the copyright notice. Improvements made in
  a fork never have to come back.
- **With MIT specifically, an explicit patent grant.** Apache-2.0 adds one
  (and a patent-retaliation clause), at the cost of a longer license and a
  NOTICE-file convention. For a project like this the difference is small.

What you keep: the fewest objections from contributors, no grey area for the
mod, compatibility with every other license, and the option to relicense later
(you can always move a permissive project to the GPL; not the reverse without
consent).

### GPL-3.0

What you lose:

- **The mod's clean standing** — the grey area above. Choosing GPL for the
  daemon and something else for the mod avoids it.
- **Some contributors and reusers.** Companies, and developers who want to
  reuse a piece elsewhere under a permissive license, avoid copyleft code.
- **Freedom to relicense.** Once others have contributed, moving to a
  permissive license needs every one of them to agree.
- **Nothing on distribution.** AUR, Modrinth and GitHub all accept it.

What you keep: any public fork has to stay open under the same terms, so
improvements cannot be taken private. Prism Launcher is GPL-3.0 — but MCShell
only *runs* Prism, it does not link to it, so Prism's license puts no
constraint on this choice either way.

### LGPL-3.0 or MPL-2.0 (for the mod)

The middle ground the mod ecosystem uses: changes to *these files* must stay
open, but combining them with other code (here, Minecraft) is fine. MPL-2.0 is
the simpler of the two — copyleft per file.

### A combination that loses the least

- **Mod: MIT or MPL-2.0.** No grey area; MPL if you want changes to the mod
  itself kept open.
- **Daemon and session: GPL-3.0 or MIT,** depending only on whether forks
  staying open matters more to you than reach.

Two licenses in one repository is ordinary — say which applies where in
`LICENSE` and in each directory. The one thing to avoid is deciding late.

## Arch first, or everything at once

**Arch first.** Most of what M9 has to do is not distro-specific — de-hardcoding
paths, the `.mrpack`, templates, `mcshell check`, the README, CI — and the Arch package
is the cheapest way to prove all of it, because on Arch every dependency already
exists exactly as this machine uses it. Measured 2026-10-14: **every runtime
dependency is in the official repositories** (`extra`, and `core` for curl),
including `prismlauncher`, `hyprlock`, `gtk4-layer-shell`, `python-i3ipc`,
`python-pyxdg` and `python-dbus-next`. The AUR package needs no other AUR
package.

Doing every tier at once would multiply the test matrix before the base is
proven, and the tier 2 and 3 work is mostly one large separate problem —
**Prism as a Flatpak**, which is how most non-Arch users get it (below). Every
bug found on Arch first is a bug not chased through four distros at once.

**But build for portability from the first commit, and ship it only on Arch.**
The cheap rules that keep tier 2 from being a rewrite:

- Paths through variables, never `/usr/share/...` written into twenty files.
- Dependency checks by *command or library*, never by package name or
  `pacman -Q`. Package names are the only thing that differs per distro, and
  they belong in docs and packaging, not in code.
- Prism's data directory looked up in one place (`session/prism/common.sh`
  already is that place), so the Flatpak location is one more branch later.
- Nothing that assumes GDM, Intel graphics, or a laptop. The code already
  degrades without a battery and without a backlight; keep it that way.

## The Arch package

- **Start with `mcshell-git`** — a VCS package that builds from the latest
  commit. It is the normal first AUR package for a project still moving, and
  testers always get the current code. Add `mcshell` (pinned to tagged
  releases) once a version is worth pinning.
- **Do not build the mod in the PKGBUILD.** Fabric Loom downloads and remaps
  Minecraft as part of every build: minutes of network access and a Gradle
  cache on the user's machine, which is a heavy thing for a package build to
  do. Have CI build the jar on each release and the PKGBUILD download it. The
  jar holds only our classes, so it can be published.
- **Install to standard locations:** `/usr/share/mcshell` (session scripts,
  assets), `/usr/lib/mcshell` (the daemon), `/usr/lib/systemd/user/` (the
  units), `/usr/share/wayland-sessions/mcshell.desktop`. Nothing in `$HOME` at
  install time.
- **Per-user setup is a command, not a package hook.** A package installs
  system-wide; the Prism instance, the world and the Microsoft sign-in are per
  user. `mcshell setup` (import the `.mrpack`, copy a template world) run once
  by each user, then the sign-in in Prism.
- **Dependencies:**
  - `depends`: sway, swaylock, python, python-i3ipc, python-pyxdg,
    python-gobject, gtk4-layer-shell, prismlauncher, jdk21-openjdk, systemd.
  - `optdepends`, each with what it adds: hyprlock (the lock screen's password
    field), python-dbus-next (notifications), pipewire-pulse and wireplumber
    (the Sound page and volume bar), networkmanager (the Network page and
    offline boots), grim and wl-clipboard (F2), brightnessctl, playerctl,
    librsvg (SVG icons), bluez-utils (Bluetooth), imagemagick (lock-screen
    fallback), socat, foot.
- **Test it with `namcap`**, and install it in a clean chroot
  (`extra-x86_64-build` from `devtools`) so a dependency that is only present
  because this machine has it gets caught.

## Distros

| Tier | Distros | Why |
|---|---|---|
| **1 — supported, first** | Arch; EndeavourOS and CachyOS through the same package | home distro; every dependency in the official repos; native Prism |
| **2 — should work** | Fedora (official Sway spin), openSUSE Tumbleweed, NixOS | recent packages. Prism mostly as a Flatpak, so this tier is gated on the Flatpak work |
| **3 — best effort** | Debian 13, Ubuntu 24.04+, Pop!_OS, Mint | older packages. Check before promising: whether `gtk4-layer-shell` and `hyprlock` are packaged. swaylock covers locking either way |
| **Worth a look** | Bazzite and other immutable Fedoras | a gaming audience; packages layered onto the immutable base, Prism Flatpak-only |
| **Out of scope** | no systemd (Void, Artix, Alpine, Gentoo on OpenRC); X11-only | user units and logind are built in |

**Prism as a Flatpak, the work tier 2 is waiting on.** Three things break:

1. The instance moves to `~/.var/app/org.prismlauncher.PrismLauncher/data/PrismLauncher/`.
2. The sandbox hides `$XDG_RUNTIME_DIR/mcshell.sock` from the mod, so the mod
   cannot connect. Needs a permission override
   (`flatpak override --filesystem=xdg-run/mcshell.sock`), applied by `setup`.
3. The game runs in its own PID namespace, so the Statistics screen's
   protection of the game process — found through `SO_PEERCRED` on the
   socket — sees the wrong PID. Needs re-measuring under Flatpak before
   anything is changed.

Hardware, stated up front in the README: **one monitor** (a locked decision);
**Nvidia's proprietary driver** works but is sway's unsupported path; hybrid
graphics is the configuration the shell was built and tested on.
